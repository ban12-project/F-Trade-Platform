# Workflow v5 migration (#821)

## Summary

Selected `workflow@5.3.0` on 2026-11-04, the stable npm `latest` and the
[2026-11-02 release](https://github.com/vercel/workflow/releases/tag/workflow@5.3.0).
This is an infrastructure-only migration. Human approval authority, product
facts, quote/delivery confirmation, video content, prompts and creative choices
are unchanged; the marketing-video ABCD creative review is not applicable.
No performance benefit has been measured or is claimed.

**Do not promote this migration until the deployment gates below are verified.**
A passing local historical fixture does not prove that the project's old Vercel
deployments still exist, or that a real outstanding approval can be resumed.
No production run, database, deployment or retention setting was changed by this work.

### Narrow transitive serde exception

The existing AI SDK provider-utils dependencies carry `@workflow/serde@4.1.0`,
and `@vercel/sandbox@3.2.1` carries `4.1.0-beta.2`. These packages contain only
the identical two `Symbol.for` serialization markers, with no execution engine
or dependencies. They are not a mixed v4/v5 runtime. Do not force an unrelated
SDK across a major version to make a textual dependency scan green.
`test-workflow-serde-compatibility.mjs` checks all installed importer boundaries,
AI SDK reexports and an actual Sandbox class round-trip through the v5 serializer
without HTTP. The v5 runtime itself resolves serde 5.0.0.

## Behavior Changes To Review

Based on the [official v4-to-v5 migration guide](https://github.com/vercel/workflow/blob/workflow%405.3.0/skills/migrating-workflow-v4-to-v5/SKILL.md):

- **Historical event logs are incompatible.** v5 events are run-local sequence
  slots, not ULIDs. Never copy, rewrite, regenerate, retarget or replay a v4 run
  in the v5 runtime. The frozen fixture is completed by its own v4 code.
- **Deployment affinity:** Vercel keeps an in-flight run on its creating
  deployment. Retention must still be verified for this project. The regression
  test invokes actual v5 `resumeHook` with a fake transport and frozen v4 run
  metadata, checking original deployment/spec-version routing and write-before-
  wake ordering. This is not a live Vercel or production authorization test.
- **Linked tracing:** no repository dashboard/query depends on a single trace ID
  per run. Use `workflow.run.id` for new diagnostics. Verify out-of-repository
  dashboards before promotion; use `WORKFLOW_TRACE_MODE=continuous` only if a
  reviewed consumer requires the old layout.
- **Per-run event ceiling:** Local/Vercel default to 25,000. Sandbox has 100
  observations and 15-second durable sleeps; catalog submission caps each batch
  at 20 records with concurrency two; video workflows have one top-level step;
  Human Gate has one hook. No unbounded production workflow loop was found.
  Retries can add events; the runtime limit is a failure boundary, not a promise
  that arbitrarily repeated failures will succeed.
- No app event key decodes a Workflow event ID or treats it as globally unique.
  Database `workflow_event` is the separate business state/audit contract and
  is not the SDK event log. Correlate SDK events by `(runId, eventId)`.
- Turbo mode is now on; no explicit `WORKFLOW_TURBO` override was found. No
  `WORKFLOW_PRECONDITION_GUARD` setting was found in tracked configuration.
  Check deployed environment variables separately.
- Hook metadata is lazy/async. No production `getHookByToken` or `resumeHook`
  call exists in this checkout; the new tests await metadata. The existing
  `/api/workflows/human-gates` endpoint starts runs only. Identify and verify
  the actual approved resume operator/integration before rollout. Do not add
  an unauthenticated resume endpoint as a migration shortcut.
- Error class identity is preserved. Existing business handlers remain unchanged;
  SDK error message matching was not found. Stream leading-chunk flush is now
  immediate; no app direct-stream/coalescing dependency was found.
- Generated host bundles are ESM; no app post-processor was found. Duplicate
  workflow/step IDs now fail the build; the build passed without suppressing it.
- No world-postgres/custom World is used. Local stream storage changed; preserve
  any old local directory with its matching v4 checkout, and use a fresh v5 test
  directory. Tests clean only their own newly-created synthetic directories.
- No workflow body uses WeakRef, FinalizationRegistry, Atomics.waitAsync or async
  WebAssembly. Node/provider operations remain inside existing steps.

## Deployment and rollback gates

Before allowing the first v5 production run:

1. Privately inventory nonterminal runs by run ID, original deployment, SDK
   version and pending hook owner. Include long-lived approvals. Keep business
   payloads, customer information and credentials out of Issues/PRs.
2. Verify each referenced v4 deployment is still accessible and its retention
   policy protects it until all its runs finish. Record the verified policy and
   owner in the private operational record. An immutable deployment URL alone
   is not retention evidence. If a deployment is missing, stop and resolve the
   stranded run with the owner; never replay its log under v5.
3. Verify the authorized Human Gate resume integration/operator, current human
   identity and approval permissions. Start a synthetic v4 gate on a retained
   deployment, switch only the test caller to v5, resume the old hook, and show
   that execution and completion stay on v4 with no duplicate business writes.
   Run this in an authorized staging context, not using a real approval.
4. Verify application environment World selection, original deployment routing,
   removed precondition env var, trace consumers, and all business acceptance
   cases with a dedicated synthetic PostgreSQL/provider setup. No production
   DB migration is required by this dependency migration.
5. Run the applicable local checks at the final commit and attach exact results.
   The temporary CI pause is not evidence of correctness. Keep draft status
   until unresolved gates are cleared; do not mark #821 fully accepted merely
   because compilation passed.

Rollback: send new starts back to the retained, known-good v4 application
version through the authorized deployment procedure. Keep both deployment
versions available for their own in-flight runs. Never make v4 consume v5 slot
logs, never send v4 logs to v5, and never cancel/recreate a business run merely
for rollback without separate owner authorization. Verify pending hook routing
and duplicate fences after the switch. A rollback does not undo completed
business side effects. Non-Vercel operators must retain separate v4/v5 stores
and workers until v4 runs finish; no automatic state-format migration is offered.

# 扫描目录内部编号与 OEM 单元格补缺

关联 #268、#5 和 [PR #569](https://github.com/ban12-project/F-Trade-Platform/pull/569)。本轮修复明确表头的扫描目录候选发现与同一行证据，不关闭完整 M1 验收。

## 已验证的缺口与修复

初始整页 OCR 包含部分正确编号文字，但没有结构化标签／行列绑定，既定十个样本均无法自动发现。新增已核对的 TQ NO.／天奇编号内部编号标签及 OEMNO. 字面标签，候选发现、字段校验、位置和提示词保持一致。组件编号不能成为 OE；车辆类型、摩擦片和花键缩写不获得车型或整件规格语义。

可选的本地 OCR 复读先要求唯一、明确的 ITEM／TQ NO.／OEM NO.／PART NO. 相邻表头，再从扫描像素中的实际表格线确定内部编号及 OEM 单元格。每个编号和 OEM 都来自自己的单元格复读；低置信度、破损标签、无法确定的边界或字面编号检查失败时不恢复该行。不改写字符，不按已知期望值修补，保留原始 OCR、物理页和所有独立标签记录。可选处理最多每页 60 秒、每份文件 120 秒；超时回到原始可读文本。

## 参考资料诊断

用户已授权 reference 作为真实 SKU／图片事实与素材权利来源，并委托本次审核。原件与逐条期望值留在受控本机记录；此报告只保存研发聚合值。

完整 32 页扫描目录实际经 Poppler/Tesseract 和生产 Python 转换入口处理，32 个物理页边界保留。此前转换的候选为 72，本轮为 91；两页表格新增 19 条。既定 A/B 十个样本中，八个被恢复，内部编号及各自同一行 OEM 与此前冻结的原页核对值逐字一致；另两个未恢复。八条均通过实际候选发现、自己的字段位置及草稿校验，仍为 review_required 且缺失阻断保留。91 是发现数，不是准确率或已审核 SKU 数；未逐字段核验全部新增行。

该完整文件诊断用于发现覆盖；最终运行镜像的相同两页与云端部署复验另行追加。更早的边界定位、字体／分割、严格置信度及可选处理未触发等失败保留在忽略目录，没有覆盖成通过。

## 回归与交付边界

已通过候选标签、字面 OCR、坏标签、无网格、缺失行线、低置信度、相邻行 OE、组件编号冒充 OE、车辆类型冒充车型、缩写冒充规格、独立原记录保留及物理页回归。合成 PDF 实际执行离线 Poppler/Tesseract，并验证初次表头识别损坏后独立复读、可选处理超时回退。已有原生表格、套件空间隔离、混合／空白页及 Product Agent 契约／生产评测规则回归保留。

文档镜像与源码白名单包含新模块，构建上下文仅五个受控源码文件；原始目录、环境变量和依赖树不进入镜像层。实际 amd64 镜像禁网回归通过；最终 head CI、合并和生产固定摘要部署证据另行追加。仅应用重新部署不能更新已固定的文档镜像。

本轮新增 ProductReady、模型请求、渠道发布、客户消息、报价和交期审批均为零。完整事实／图片逐字段验收、其余十个真实候选的身份缺失、20 槽位最终 Ready 和 M2 平台业务验收仍未满足。

## 运行镜像差异复验

首次实际 Ubuntu／Tesseract 5.3.4 镜像读取同样两页，仅恢复四个既定样本；本机 Tesseract 5.5.3 的八个不能据此视为生产结果。原失败保留。直接三百 DPI TSV 诊断确认旧版本损坏了不参与事实提取的规格表头，过强的整表表头前置条件拒绝了第二页。修复后仅要求提取列的明确相邻表头、置信度和实际单元格边界，其他列不参与事实提取或标签修补。

更新的实际 amd64 镜像在禁网环境重新处理两页，恢复 16 条未审核行。既定十个样本中八个编号与自己的 OEM 逐字一致，另两个仍未恢复，与本机既定样本结果一致；新增行总数因 OCR 版本不同而不强求一致。合成坏规格表头回归独立验证这项修复，坏身份／OEM 表头和行界仍拒绝。

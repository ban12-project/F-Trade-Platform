# Complete VPS smoke-chain portability — 2026-11-01

Related to #739 and #718. The second attempt of release
`739088b76b83e7e90bc7d2044b05d39e4cc08b06` passed image startup, H.264 decoding,
full-DOM negative controls and the first native profile read/write checks, then
failed because test-native-profile-runtime.sh also invoked host Node. The
earlier configuration generator fix was necessary but not sufficient.

Audit of all three scripts in the image acceptance call chain found another
host Node generator in test-browser-observation-images.sh. Both are fixed:

- Native profile shutdown uses the already required Python subprocess runtime
  with the same 35-second timeout, checked Docker exit status and subsequent
  runtime exit/state assertions.
- Observation fixture configuration is generated by Node inside the exact Agent
  image, without network or a writable root, with dropped capabilities and
  128 MiB / one CPU limits. The host receives only JSON stdout.
- The optional seccomp array uses the Bash 3-compatible empty-array expansion
  already applied to the native-profile fixture. It does not remove seccomp or
  weaken container resource/isolation checks.

## Actual VPS verification

The full test-browser-images.sh chain ran against the exact Agent/browser pair
tagged with `739088b...`, using an isolated copy of tracked fixture sources and
these two changed scripts. The SSH test process exited **0**. This is a candidate
image test, not a claim that these scripts or the runtime were already promoted.

Observed passes include startup, lease expiry, full-DOM inspection, legacy
profile migration, empty-profile first use, replacement-container recovery,
cookies/localStorage/nonextractable-key retention, cross-account rejection,
1400x860 window persistence, six publication-observation scenarios and four
inbox scenarios. All observation cases report zero external effects. Effective
kernel isolation checks passed; observation memory peak was 610365440 bytes,
PID peak 168, and memory/PID limit and OOM event counters were zero.

Shell syntax and ten release-driver tests also pass. No real account, message,
publication or existing account volume was used. Full rollout remains pending.

## Earlier disk admission failure

The first attempt of `739088b...` stopped before build because free disk was
11829850112 bytes, below the unchanged 12 GiB threshold. A stopped Docker build
container from the earlier TARGETARCH failure and its unreferenced image chain
were positively identified and removed without force. Free disk rose to
12942151680 bytes; only then was that failed release retried. The current
runtime image, recovery archives and account volumes were preserved. Later
builds still need their own disk admission check; this receipt is not a durable
capacity guarantee.

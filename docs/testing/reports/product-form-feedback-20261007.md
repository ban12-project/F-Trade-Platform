# 产品表单反馈同步修复 — 2026-10-07

关联 [#519](https://github.com/ban12-project/F-Trade-Platform/issues/519)，生产试点资料范围见 [#268](https://github.com/ban12-project/F-Trade-Platform/issues/268)。来源选择修复 [#518](https://github.com/ban12-project/F-Trade-Platform/pull/518) 已上线；随后实际生产表单暴露另一项独立的反馈问题。

## 问题与修复

输入三项核心身份事实并分别选择证据后，完成度仍显示 0%，批量绑定目标仍只有初始产品类型。实际保存及刷新后的三项字段和证据均存在，不能将显示失步解释为资料丢失。

`ProductFields` 接收稳定的表单对象，却在子组件中依赖 `form.watch()` 返回值。当前编译配置下，字段变化没有及时更新这个区域的派生界面。本机合成输入复现同样的 0% 和缺失目标；新增回归在修改前失败。

现在使用 `useWatch({ control: form.control })` 在字段区域订阅值变化，并从同一快照计算进度、目标和套件控制状态。现有产品类型标签补上与控件的关联，便于按名称操作。保持 Cache Components、默认 Turbopack、两个 React Compiler 开关、RHF/Zod 和现有 shadcn 控件；服务端授权、校验、保存和业务门禁未改动。

## 验证

- 真实运行的本机应用中，三个有事实和证据的字段立即显示 16%，名称和编号也进入批量目标。没有先改变批量选择状态来触发一次额外渲染。
- 回归覆盖输入/清空事实、分别选择证据、切换套件后启用控件及调整进度分母、补充套件证据后增加进度、切回单片后清空套件及其证据并禁用控件。
- 修改前的测试失败和 trace 保留。首次修改后，测试到达正确进度，又因同名批量复选框与名称输入框产生定位歧义而失败；改用 textbox/combobox 的语义角色后，完整用例通过。没有放宽断言或添加重试。
- Agent 浏览器观察与上述回归交叉验证；实际组件 React 检查成功，嵌套属性会被工具截断，不把它当作完整表单快照。Next 开发服务器的浏览器错误和编译问题均为空，类型检查通过。

本机使用既有合成测试账号、新临时项目及仅含元数据的合成证据；不读取云原件，不保存产品事实，不运行模型或业务审批。生产复验只检查未提交表单的反馈，不增加生产产品记录。

## 正式验收边界

#518 的线上检查已确认部署 READY、已有文件原名、一个部分参考测试草稿的三项绑定及正常页面链接的私有 PDF 预览；匿名来源请求为 403。原生 PDF 调试重载和自动页码控制受到浏览器工具限制，原失败保留在脱敏检查点，不能冒充完整浏览器字节/页码验证。

本修复使操作反馈跟随当前输入，不证明产品事实完整或已核实。既有部分草稿仍缺少 OE 或完整适配信息，也没有原始实物图片；正式渠道、真实 RFQ 和具名业务审核仍待验收。六项真实业务统计及 decision pending 保持原口径。

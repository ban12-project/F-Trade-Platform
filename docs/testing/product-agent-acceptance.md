# Product Agent 验收矩阵

本矩阵定义 20 个试点产品的执行标准。config/product-acceptance.yaml 预留 20 个槽位并按 A–D 各 5 个分配。

`docs/reference/` 测试资料已获[用户持续测试授权](../reference/README.md#持续测试授权2026-09-05)，可以直接用于测试批次，不等待 #6 或重复人工授权。测试批次单独标记为 test-only，测试分支的审批决定不冒充真实人员审核。以下事实指标仍照常执行；错误和缺失不能因测试授权改成通过。

真实工厂试点仍使用 #6 及真实 Gate 01 的验收口径；该口径不阻塞用户已允许的测试迭代。

## 单产品判定

每个产品都必须满足以下条件：

1. 所有源资料中应识别的字段均被准确识别，字段识别率为 100%。
2. OE 仅允许去除首尾空白后比较，集合必须完全一致；不能增加、删除或改写。
3. 品牌、车型和应用信息不能新增或改写；不确定值必须保持缺失并进入人工确认。
4. 所有预期阻断缺失字段都必须被识别，阻断缺失召回率为 100%。
5. 最多经过一轮人工修订后，blocking_missing_fields 为空、每个已填写事实都有字段级证据，并具有有效的 Gate 01 人工批准，才算 Ready。

字段识别、OE、车型和阻断缺失都是事实安全指标，因此不采用低于 100% 的“平均分抵消错误”。审核耗时记录从送审到人工决定的秒数，首轮真实试点只报告中位数和 P90；目前没有证据支持任意设置通过时限，所以它暂不作为通过阈值。

## 执行步骤

1. 为每个获授权 SKU 选择一个尚未绑定的 pilot-slot-01 至 pilot-slot-20，并按 A–D 协议准备输入。
2. 在运行前固定源资料、期望字段、期望缺失字段和证据引用；测试后不得修改期望值。
3. 保存每次运行的唯一 run_id、起止时间、五项指标、人工修订轮次和 Ready 结果。
4. 失败结果必须符合 ProductAcceptanceResult 契约并填写新的 GitHub 研发 Issue URL。Issue 只写 synthetic 运行标识和缺陷复现，不附真实业务数据。
5. 修复后创建新的运行记录；旧失败记录不可覆盖或改写为通过。目录 CLI 的每次新批次必须指定未使用的 `--output` 路径；路径已存在时会在抽取开始前失败退出，当前批次内部仍以原子写入更新报告。

## 批次判定

只有 20 个槽位均执行且单产品全部通过，M1 的产品验收才通过。任何未运行、失败、证据缺失或超过一次人工修订的产品都会使批次保持未通过。审核耗时单独汇总，不影响首批事实安全结论。

## 标签与原样提取

车型、应用和品牌的已审查标签统一维护在 `lib/product/source-labels.ts`，提示词、证据定位和服务端校验共用该映射。`Fit Model` 已经原页面与转换表格核对，仅映射到 `product.vehicle_model`；不能映射到应用或拆出品牌。通用 `Model` 不属于别名。

这三个字段仅允许去除首尾空白后逐字比较，保留大小写、标点、缩写和整个单元格值。拆分、展开、概括或跨字段重分配会被拒绝。`Disc PTO` 等部件栏中的 `OD`、`Spline`、`Mat` 不能直接作为整件产品规格；无法明确映射的事实保持缺失并待复核。

Issue #282 的诊断应分别记录原页面、转换后的候选行和模型原始响应；受控内容仅保存在本地。标签修复后的抽取成功也不等于 Ready 或 20-slot 字段完整率通过。

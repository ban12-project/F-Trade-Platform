# Reference 资料的 mock 后续流程

用户在 2026-09-05 明确指出 PDF 没有缺失信息，并要求 mock 后继续。此授权允许在测试副本上补充合成内容，不再把补充工厂资料作为这条测试路径的前置条件。

`scripts/reference-mock-workflow.ts` 的 `runReferenceMockWorkflow(source, draft, slot)` 使用此前校验过的目录来源与草稿，执行以下流程：

1. 重新校验原字段及其逐字段来源；原字段篡改时拒绝运行。
2. 确认不完整草稿不能直接批准，执行一次模拟拒绝。
3. 为缺失的名称、类型和 OE 建立独立的 `synthetic:mock-supplement-*` 来源，原字段和来源引用保留。类型枚举本身不含 MOCK 前缀，其合成性质由来源与外层分类明确标记。
4. 重做字段证据校验，验证删除证据后仍无法批准，执行模拟测试批准。
5. 将该测试产品传入 synthetic 后续流程，关联内容与 RFQ，执行模拟报价、跟单、交付确认和商机状态转换。

返回值固定标记 `reference_with_synthetic_supplements` 和 `local_domain_simulation`，同时明确没有业务数据库写入、真实发布或工厂审批。参与者是 `synthetic-test-reviewer`；契约中的 human 角色在此代表模拟角色，不代表有真人执行。所有导出的 Ready 对象必须留在这个测试封装内，不能直接作为业务产品导入。

## 本地执行证据

20 条原目录草稿已逐条执行。每条初始批准均被缺失校验拦截；补充后一次模拟修订完成，20 条成为测试 Ready，20 条关联流程到达 OPPORTUNITY，总计 280 次状态转换。逐条输出包含合成字段列表、独立来源、原始引用、测试决定和下游结果。原 PDF SHA-256 前后相同，原草稿与来源对象未被修改。

受控派生结果仅保存在本地；仓库不包含目录编号、OE、车型或模型正文。该结果证明 mock 补齐后的领域流程可执行，不证明真实资料完整、模型重新抽取准确率、A–D 图片覆盖、数据库/浏览器全流程或真实账户发布。之前的 18/20 失败批次及另轮 2/2 结果继续保留。

## PostgreSQL 持久化回归

`scripts/test-product-stream-postgres.ts` 在独立、仅 loopback 可访问的 `f_trade_stream_test` 数据库中调用 `test-mock-product-persistence.ts`。CI 使用 20 条完全合成的来源，运行同一 mock 补充逻辑，再调用实际的草稿插入与审核事务；不会将本机 reference 派生字段上传到 CI。

测试回读产品状态和版本、项目关联、原始与 mock 字段证据、实际生成的批准引用、事件和审计。错误版本、错误审批 ID、并发重复批准，以及缺字段证据的批准都必须保持原子性。持久化前先移除领域模拟中的批准引用，以数据库审核事务生成的新引用为准。

该检查扩大了真实 PostgreSQL 事务覆盖，不代表已完成 reference 文件的登录态浏览器导入或部署数据库验收。本机未配置 PostgreSQL 时，实际数据库执行证据以 CI 对应检查日志为准；不能用 TypeScript 通过替代数据库测试。

## 登录态浏览器与隔离数据库验收

Issue #291 使用 `playwright.database.config.ts` 在 CI 的独立
`f_trade_browser_test` PostgreSQL 数据库运行纯合成浏览器测试。它访问实际
`/workspace` 页面，经产品创建和 Gate 01 的 Server Action 写入数据库，再回读
产品版本、逐字段证据、审批、项目关联和审计记录。测试构建关闭 testing API，
不使用 `/testing` 页面或替代 Action。

账号和签名会话由测试预置；覆盖未登录页面拦截与登录后的实际操作，不覆盖邮件
验证码登录、证据文件上传或真实工厂审批。证据记录和产品名称明确标记 MOCK，
测试数据库由 CI 服务销毁，不连接已保存的业务数据库。此测试使用纯合成数据，
不把原始 PDF 或本地参考资料派生内容提交到 CI。

默认数据库连接仍使用 Neon。只有显式设置 `DATABASE_TRANSPORT=postgres` 才会
启用原生 PostgreSQL 连接，且仅接受 loopback 主机；未知配置和远程地址会被拒绝。

## Kimi 内容生成验收

Issue #293 将 `openai-compatible` 模型明确连接到 Chat Completions；`openai`
配置继续使用 Responses。请求级回归检查实际路径、选定模型、证据传递、结构拒绝，
以及结构化产品事实仍须逐值匹配。它们使用合成响应；实际 Kimi 调用结果另存本地。

`lib/content/generation.ts` 与内容 Server Action 共用生成逻辑。测试调用显式选择
`kimi-k3`，从本地 mock 产品副本取名称和一项有引用的字段，并设置 `syntheticTest`。
生成文案保持 MOCK 标签，内部字段名及证据编号不应写入客户文案；结构化内容记录
仍由服务端绑定原证据。视觉说明仅描述抽象背景、排版与文字卡片，避免将禁止描绘的
工程词写入说明后触发校验；不会放宽现有视觉校验。

首轮两条实际请求均返回文案，一条通过内容构建校验，另一条因否定句中的工程词被
视觉规则拦截。首轮结果保留，提示调整后的两条复测通过。扩大批次及逐条审阅结果
以本地独立运行报告和 Issue #293 记录为准，不把跨轮复测写成单轮成功率。

扩大批次的审阅还发现车型列表被展开、重新加空格或连接词。共用生成函数因此增加
车型和应用原文检查：提供了这两类字段时，客户文案必须保留完整原字符串；未出现
原字符串则拒绝返回草稿，不能只凭结构化 `product_facts` 正确就判文案通过。
这项必要条件仍无法证明文案没有其他额外主张，后续内容审核保留。

这里的成功仅指模型输出通过结构、MOCK 标签和内容构建校验。生成内容保持
`review_required`；不证明所有自然语言事实均正确，不代表真实工厂批准、内容审核
或渠道发布。测试不写业务记录，也不提交原始或派生产品文案到 GitHub。

## 实际文案接入审核与后续演示

Issue #295 允许 `runSyntheticDemo(testProduct, testContent)` 接收本地实际生成的
待审文案。入口拒绝不匹配的产品、非测试内容标识、预先批准的文案，以及不符合
所选产品字段值和证据的结构化事实。提供文案时不会用预置文案覆盖它。

20 条最终 Kimi 文案已逐条进入本地域模拟，完成模拟内容审核、发布回执、询盘、
RFQ、报价与跟进，达到 20 个 OPPORTUNITY，共 280 次状态转换。输出记录实际输入
文案的哈希和内容 ID；审核与模拟发布前后的正文哈希一致，原待审文件未修改。
这里的发布、审批及商机均是模拟状态，没有真实外部发送或业务数据库写入。

隔离 PostgreSQL 浏览器测试另外通过真实内容表单和 Server Action 创建待审内容，
再提交测试审核决定，回读正文、结构化产品证据、版本、审批、项目关联及审计。
CI 文案是纯合成对照，不含本地 Kimi 文案或参考资料派生字段；不能把两层证据合称
为参考资料已完成浏览器全流程。文件上传和销售阶段的完整浏览器链路仍需继续验收。

首次内容浏览器执行发现：名称和 OE 共用同一证据时，事件中的重复引用被 Workflow
拒绝，导致创建事务回滚。创建、复制及修订流程现在统一将事件证据整理为唯一列表，
保留 `product_facts` 的每个字段绑定。浏览器回归覆盖创建、退回、修订、再次批准，
并核对事件引用唯一且逐字段证据没有丢失。
